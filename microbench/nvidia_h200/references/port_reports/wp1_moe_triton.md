# WP1 (wp1_moe_triton) H200 report: Triton fused-MoE operand-stream services

Branch `h200-port-wp1_moe_triton`, baseline `d6ef48a08`; probe code commit `48abf63b1baff96101be2f06194dc27a1d246932` (the `source_baseline_commit` of every WP1 reference). All captures ran on the capture host GPUs 0 and 3 (NVIDIA H200, 132 SMs, driver 575.57.08), one process per GPU at a time. Remote run root: `<public-root>/h200_microbench/wp1_moe_triton/` (execution copy `repo/`, vLLM 0.11 source copy `vllm011_src/`, plan `plan.json`, logs `logs/`); raw: `repo/profiler_output/microbench/nvidia_h200/wp1_triton_moe_f31e5412_20260925/` (472 processes) and `repo/profiler_output/microbench/nvidia_h200/wp1_fused_moe_operand_service_f31e5412_20260925/`. Small raw copies (result.json, clock.csv, raw.csv; 10 MB) are in the same local `profiler_output/microbench/nvidia_h200/` paths (gitignored). No production operator or kernel duration is measured or consumed; every value is a mechanism probe re-run with the A800 selection rule.

Same probe: the H200 owner copies execute the byte-identical vLLM 0.11 BF16 `fused_moe_kernel`/`invoke_fused_moe_kernel`/`moe_align_block_size` source (`microbench/nvidia_h200/operators/fused_moe/vllm_0_11_fused_moe_kernel.py`, audited at run time against `vllm_src_3ver/a800/.../fused_moe.py` sha256 `8be8477a...` and `moe_align_block_size.py` sha256 `ac0bd207...`). The source compiles unchanged under Triton 3.6.0, so the vLLM 0.24 fallback was not needed. The only non-verbatim stack piece is the sort op beneath `moe_align_block_size` (vLLM 0.24 `_moe_C.moe_align_block_size`, same positional signature; the vLLM 0.11 Python wrapper keeps the 0.11 buffer sizing, which matters for `numel < num_experts` BM16 cases such as E256 16-active/241-max). Tile configs are the A800 ones (BM64/BN64/BK32/GSM8, Triton default warps/stages; BM16/BN32/BK64/GSM1). Routing and census rows are the A800 cases: every H200 capture reproduces the A800 active/maximum M-tile topology exactly (checked for all 33 references), and the exact-order cases use the canonical `kernel_dataset/nvidia_a800/fused_moe.json.zst` `tok_per_expert` rows named by the A800 references.

Clock gate: each process samples `nvidia-smi -i <gpu> --query-gpu=timestamp,clocks.sm,utilization.gpu -lms 50` for its whole lifetime. After the unchanged compile/warm-up launches, a 0.8 s L2-resident FP32 add spin raises the SM clock. The capture is accepted only if every sample inside [first timed launch - 0.1 s, last timed launch + 0.1 s] reads >= 1980 MHz. A heavy BF16 matmul warm-up was tried first and throttled the clock to 1740-1755 MHz at the power limit, which leaked into the window, so it was replaced. Result: 472/472 Triton-probe processes accepted on the first attempt, 0 rejected, window minimum 1980 MHz; W1R 32/32 case windows accepted; the operand-read probe ran 6/6 processes accepted through `microbench/nvidia_h200/compute/clock_gated_capture.run_gated` (33 busy samples, all 1980 MHz). The A800 rule "minimum over devices 2 and 6" is "minimum over GPU 0 (A800 device 2) and GPU 3 (A800 device 6)". References that the A800 captured on one device ran on GPU 0 only.

## Deep-queue gate (2*108*8 = 1728 -> 2*132*8 = 2112)

- `bm64_triton_h2880_source_depth` (yaml L943): the A800 E32 probe depth (32768 tokens, maximum 2080 M tiles) passes 1728 but not 2112. The H200 E32 cells were therefore re-chosen at 33792 tokens (maximum ceil((33792*4+32*63)/64) = 2144, active 2127/2128). The E128 depth 2174 is unchanged. As a result, the canonical E32/H2880 32768-token launch (2080 M tiles) no longer qualifies as "deep" on H200.
- `bm64_triton_e512_w2_source_depth` (yaml L542): measured depths 3064/5624 pass 2112. The A800 reference also covers the canonical depth 1784, which lies in (1728, 2112], so the H200 selector must not route 1784 to this service (recorded as `h200_capture_provenance.deep_gate_covered_depths`).
- `bm64_triton_e128_deep_w2_source_depth` (L562): depths 2174/4222 both pass 2112; the reference's `minimum_exclusive_maximum_m_tiles` is 2112.

Finding: every published Triton fused-MoE service, including the 13 BM16 ones shared with WP2, is keyed on one of two BF16 tiles: BM64/BN64/BK32/GSM8, which is the A800 vLLM 0.11 `get_default_config` for large M, or BM16/BN32/BK64/GSM1, the A800 small-M default. The H200 vLLM 0.24 stack never launches either tile for DeepSeek-V3:
- fp8 w8a8 block [128,128] uses the bundled tuned H200 file: BN128/BK128 with BM16 (GSM 1/16/32/64), BM32 or BM64.
- BF16 `get_default_config` in vLLM 0.24 selects BM16/BN64/BK128, BM32/BN64/BK128, BM32/BN128/BK64, BM64/BN128/BK64 (4 or 8 warps) or BM128/BN128/BK64.
- The observed TP4 decode trace runs only fp8 launches (100/97 registers, 0.037 MB dynamic smem = the BM16/BN128/BK128 3-stage family; 236/237 registers, 0.099 MB = BM64/BN128/BK128 4-stage). The two 97-register geometries (grid 448 and 1792) match no register count in the tuned table, but their shared memory places them in the BM16 fp8 family.

On H200, the published services can therefore price only probe-identical BF16 launches with A800 vLLM 0.11 tiles. The real DeepSeek-V3 H200 fused-MoE launches fall outside every published service signature and would be handled by whatever generic path the Forward uses for unmatched tiles. This is a generality gap for the maintainer, not something WP1 fixes.
