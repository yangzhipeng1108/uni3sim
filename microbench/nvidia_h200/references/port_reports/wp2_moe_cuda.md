# WP2 (wp2_moe_cuda) H200 report: MoE grouped-GEMM CUDA-probe parameters

Branch `h200-port-wp2_moe_cuda`, baseline `8e7ae7db16ecc531a87f394a6a229514f2a3f919`. All captures ran on the capture host GPU 1 only (NVIDIA H200, 132 SMs, driver 575.57.08). The remote run root is `<public-root>/h200_microbench/wp2_moe_cuda/runs/`, and the small raw summaries were copied to `profiler_output/microbench/nvidia_h200/wp2_*` (gitignored). No production operator duration feeds any value. Every value comes from an independent mechanism probe, from the A800 selection rule applied to that probe, or from compile-time launch metadata.

Clock gate: `nvidia-smi -i 1 --query-gpu=clocks.sm,utilization.gpu -lms 50` ran during every capture. The CUDA probes that run for several seconds (BM64 residency, empty tail) rejected a capture when any busy sample (utilization > 0) was below 1980 MHz. The Triton probes run too briefly to produce reliable busy samples, so they rejected a capture when any sample in the timed section was below 1980 MHz. The routing-atomic kernels last only 10 to 80 us, so they rejected an execution when any sample between the first and the last boosted sample was below 1980 MHz. In both cases a busy sample below 1980 MHz also rejected the execution. Rejected routing-atomic executions were repeated. The A800 rule "minimum/maximum across idle devices 6 and 7" became "across two independent clock-accepted processes on GPU 1".

Note A (sparse refill): on A800 the 1504/1568-CTA pair spans two resident W1 waves (108 x 12 = 1296). On H200 it fits in one wave (1584), so the refill mechanism is not exercised at the A800 geometry, and `sparse_refill_wave_count` = 1 makes the Forward rule add no extra fill. To check that the mechanism still exists, the H200 runner adds an H200-scaled pair from the same source (N1824/N1952, midpoint grid 1888, 1829 active CTAs, two W1 waves). There two_wave is 84184 ns and one_wave is 38456 ns, so two_wave - (2 x one_wave - fixed) = 13512 ns >= fixed 6240 ns. The second-wave refill therefore exists on H200 for launches that really have two waves (`h200_capture_provenance.h200_scaled_two_wave_pair`). If the maintainer wants the rule active on H200, it can retarget the geometry to active 1829 / grid 1888 / K32 / wave_count 2 from this same reference. Choosing the one-wave case as the 16-active case of the same source is an inference from the A800 reference geometry.

Note B (BM64 residency): the `.cu` source and `__launch_bounds__(128,5)` are unchanged. On sm_90 the operand-residency kernel still gets 94 registers and 5 CTAs/SM. The DRAM-miss pipeline kernel gets 78 registers and 6 CTAs/SM (A800: 93 registers, 5 CTAs/SM). The pipeline cases therefore ran with 792 resident CTAs: K2048 (896 CTAs) is still two-wave and K2880 (720 CTAs) is one wave. The references record `resident_ctas_per_sm` 5 (residency) and 6 (pipelines). For comparison, the H200 production BM64/BN64/BK32/GSM8 W1 launch compiles to 64 registers and 8 CTAs/SM (`bm16_grouped_gemm_launch_facts_sm90.json#facts.bm64_w1`). The A800 "five-CTA production envelope" coupling therefore does not hold on H200. This is flagged for the maintainer. The measured services are what the unchanged probe shows.
