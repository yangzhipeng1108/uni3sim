# H200 kernel capture campaign (kcampaign)

Family kernel campaigns are documented in the per-family sections at the end of this README: "Family: H200 weight-only-quantized MoE kernel campaign" (W4A16 / MXFP4 Marlin MoE), "Family: H200 KDA and DeepSeek-V4 attention kernel captures" (KDA, Kimi-K3 gated MLA, DeepSeek-V4 attention), "Family: H200 DeepSeek Sparse Attention (DSA) kernel campaign" (DSA sparse MLA, indexer, cache writes). The canonical GEMM / vector / FlashAttention / fused-MoE runners are the WP9 owner copies in `scripts/kernel_dataset/nvidia_h200/`. Every case is measured by `nsys_campaign_runner.py` under the canonical `nsys_nvtx_kernel_median` protocol through `<public-root>/h200_microbench/kcampaign/launch.sh` (writes `runs/<plan>/_provenance.json`).

## vLLM 0.30

From 2026-09-26 the remaining H200 captures use vLLM 0.30.0. Every runner supports both stacks: `installed_vllm_stack()` (`dataset_pipeline/kernel_dataset/nvidia_h200_capture.py`) maps the installed release to `vllm024` / `vllm030` and fails on any other release; version-dependent calls are explicit branches on it (no import fallback), and each window records `vllm_stack` plus the call path / backend it took in its telemetry. The 0.24 branches issue the same calls as before (checked per runner on 0.24 with the new files: identical kernel names and grids), so existing 0.24 captures stay reproducible from the corresponding versioned source snapshot.

### Environment

| Item | Value |
|---|---|
| Campaign storage | Set `MIDLAYER_H200_PUBLIC_ROOT` to the artifact root; plans and runs use its `h200_microbench/kcampaign/` directory |
| Runtime | Caller-supplied `PY` executable with CPython 3.12.3 and the stack below; installation directory is unrestricted |
| Stack | vLLM 0.30.0+cu129 (commit ced6857a), torch 2.13.0+cu129, triton 3.7.1, flashinfer-python 0.6.18.post1, nvidia-cutlass-dsl 4.7.1, tilelang 0.1.12, compressed-tensors 0.17.0; the wheel ships `_flashkda_C`, `_flashmla_C`, `_flashmla_extension_C`, `_deepselect_C`, FA2/FA3 and DeepGEMM |
| Wheelhouse | Caller-selected wheelhouse (200 cp312 wheels, 5.0 GB in the capture) |
| Fetch (the capture environment) | `pip download` of the vLLM wheel URL + `torch==2.13.0+cu129 torchvision==0.28.0+cu129 torchaudio==2.11.0+cu129` with the cu129 extra index |
| Install (the capture host, offline) | Create a CPython 3.12 environment at a caller-selected location; install the listed stack with `uv pip install --offline --no-index --find-links <wheelhouse> ...` |
| Snapshot | Caller-selected source snapshot, supplied as `REPO`; no installation directory is inferred |
| Launch | `REPO=<snapshot> PY=<runtime-python> NSYS=<profiler-executable> CUDA_HOME=<toolkit> launch.sh <gpu> <plan>__v030 --windows 3 --concurrency 1`; optional `PYTHONPATH` is preserved |

Wheelhouse preparation pitfalls: `pip download --platform` does not expand to older glibc tags, so every `manylinux_2_{5..39}` tag is listed (the capture host glibc 2.39; `nvidia-nccl-cu12==2.29.7` is `manylinux_2_18`, `llguidance` 1.7 is `manylinux_2_31`); `six` / `setuptools` are listed explicitly because pip evaluates their `python_version > "3.11"` markers with the host Python 3.10; the exit code is captured before `$(date)` resets `$?`. the capture environment has 4 GB RAM: pip re-reading a cached 930 MB torch wheel is OOM-killed, so cached wheels were extracted from the pip HTTP cache and their sha256 checked against the PyTorch index. `flashinfer-cubin` is published only on GitHub releases and is not installed; no SM90 path captured here needs it.

Plans for 0.30 are copies `plans/<name>__v030.json` of the 0.24 plans (same cases, results in `runs/<name>__v030/`), plus new 0.30-only plans generated by the family generators. Smoke windows (1 window, GPU 3, `--concurrency 1`, 1980 MHz before/after NVTX) already sit in `runs/<plan>__v030/` and were taken with the final runner files, so a campaign run reuses them as window 1.

### Per-runner status and version drift (same case, 0.30 vs 0.24)

- Canonical `gemm_runner.py` / `vector_runner.py` / `flash_attn_runner.py` / `fused_moe_runner.py`: no call-path change on 0.30. On SM90 `UnquantizedLinearMethod` still runs `F.linear` / cuBLAS (the FlashInfer BF16 GEMM is SM100-only); `ops.rms_norm` / `ops.fused_add_rms_norm`, `RotaryEmbedding.forward_cuda`, `SiluAndMul.forward_cuda` and `reshape_and_cache_flash` keep signatures and kernels; `FLASH_ATTN` / `FLASH_ATTN_MLA` stay first and reach FA3 through the pass-through `FA4DenseAttentionKernel`; unquantized MoE is still `TritonExperts` / `fused_experts` (`SWAP_AB`, `USE_TD` off for BF16). Drift: the MoE top-k reduction is `vllm::moe::moe_sum_vec_kernel` instead of ATen `reduce_kernel` (7 -> 6 kernels at 32k tokens, about 7% faster); GEMM (nvjet / split-K), vector, FA3 paged and MLA decode kernels and grids are identical. Smoke 25/25 windows over 9 plans (the 24.5 ms M16384xN151936 GEMM and the B4 S8192 FA prefill needed clock retries).

- `kc_wq_moe_runner.py`: SM90 selection unchanged (K2.6 INT4 -> WNA16 MARLIN, DeepSeek-V4 MXFP4 -> `Mxfp4MoEMethod` MARLIN, K3 compressed-tensors MXFP4 -> `CompressedTensorsW4A4Mxfp4MoEMethod` -> `MarlinExperts`); the runner checks at run time that TrtLlm-MXINT4 / TrtLlm-MXFP4 / DeepGemm-FP4 / Cutlass-MXFP4 are unsupported on the device. The 0.30 branch calls `fused_marlin_moe` as `MarlinExperts.apply` does (`ApplyMoEActivationConfig`, `FusedMoEExperts.activation`, `MarlinExperts.moe_sum(in, out, topk_ids, expert_map)`; conversion without g_idx / sort indices; `check_moe_marlin_supports_config`). Drift: EP no longer runs `output.zero_()` (8 -> 7 kernels); `moe_sum` is `moe_sum_vec(_dynamic)_kernel` instead of ATen reduce; the V4 clamp activation under EP is Triton `_swiglu_limit_pad_aware_kernel`; the Marlin M-block uses `ceil(M*E_local/E_global)`; Marlin / align / fill kernels unchanged. Kimi-K3 now runs natively: `--activation situ` (0.30 only) with the config betas (4.0, 25.0) -> `vllm::situ_and_mul_kernel<BFloat16>`, plan `kc_wq_moe_mxfp4_kimi_k3_situ__v030`; `kc_wq_moe_mxfp4_kimi_k3__v030` stays the SiLU stand-in. K3's latent down/up-proj GEMMs, router and RMSNorm around the experts (`LatentMoERunner`) belong to the GEMM / vector families.

- `kc_kda_runner.py` + new `kc_k3_mla_runner.py`: `vllm_*` ops keep names and NVTX boundaries but replay 0.30 `KimiGatedDeltaNetAttention._forward` (kernels from `models/kimi_k3/nvidia/ops/third_party/kda`, row-strided merged-projection views, beta sigmoid inside the kernels); `fla_*` (FLA 0.5.2) unchanged and working with torch 2.13 / triton 3.7. Drift: decode `kda_gate_fwd_kernel` + `fused_recurrent_gated_delta_rule_fwd_kernel` -> one `fused_recurrent_kda_packed_decode_kernel`; conv decode 3 launches -> 1 packed; chunk prefill 12 -> 9 kernels (`kda_gate_chunk_cumsum_vector_kernel`, `chunk_kda_fwd_kernel_intra_token_parallel`, `chunk_kda_fwd_kernel_inter_solve_fused`; about -30% at T16384); o_norm grid doubled. Kimi-K3 native (`k3_*` ops, 0.30 only, vLLM's own `resolve_kda_*_backend` evaluated on the H200 and recorded): prefill = 3 x `causal_conv1d_fn` + FlashKDA (`_flashkda_C`, the SM90 auto choice) or the triton chunk with `lower_bound`; decode = triton packed decode at every head count, because `torch.ops._C.fused_kda_decode` is built only by CUDA >= 13 and is absent from the cu129 wheel; MTP spec decode covered (K3 config has `num_nextn_predict_layers 0`). K3 gated MLA: `get_attn_backend` returns `FLASH_ATTN_MLA` (bf16 KV, hybrid block 768 at TP8 / 384 at TP16); `kc_k3_mla_runner.py` runs the decode branch (W_UK bmm, `fusedKimiK3MLADecodeQConcatKVCache`, FA3, W_UV bmm, sigmoid gate); `kc_kda_k3_gated_mla__v030` (flash_attn_runner) remains valid for the FA3 kernel alone. o_norm is the explicit `forward_cuda` Triton kernel on both stacks (a default `VllmConfig` would dispatch `forward_native`). Not covered: FlashKDA prefix-cache checkpoint branch, K3 MLA prefill, native fused decode (not buildable for cu129).

- `kc_v4attn_runner.py`: V4-Flash / Pro (`DeepseekV4ForCausalLM`) still resolve to `models/deepseek_v4` (not `deepseek_v41`) with `DeepseekV4FlashMLAAttention` (FLASHMLA_SPARSE_DSV4) on SM90; decode, the `fp8_ds_mla` layout (584 B/token, 576 B alignment, 64-token SWA pages, `256/ratio` compressed pages), the FlashMLA API and `get_compressed_slot_mapping` are unchanged. 0.30 branches: prefill `combine_topk_swa_indices` writes into preallocated buffers (`fill_(-1)`, `max_image_tokens=0`); the compressor calls `_SAVE_PARTIAL_STATES_KERNEL` + `_SPARSE_ATTN_COMPRESSOR_CUTEDSL_KERNEL`; first-layer mHC is `mhc_pre_broadcast_tilelang` on the 2-D embedding. 0.30 skips the C128 compress kernels in non-FULL-cudagraph steps where no request crosses a 128 boundary: the runner records `c128_boundary` / `c128_skip_rule`, always measures the FULL-graph step and refuses a boundary-free C128 prefill (the C128 decode cases B1/B8/B32 at CTX65536 have no boundary, B128 has). Drift: FlashMLA kernels renamed (`sm90::decode::sparse_fp8::` -> `sm90::decode::sparse::`, `sm90::fwd::sparse_attn_fwd_kernel` -> `sm90::prefill::sparse_fwd::sparse_attn_fwd_kernel`, same grids and times); Triton kernels appear as the generic name `kernel` (new JIT launcher); cutedsl kernels get new mangled names; the prefill dequant-gather grid is data-sized ((1,1024,1) -> (1,4096)/(1,5120) at Q16384); `mhc_pre_big_fuse_broadcast_with_norm_tilelang_kernel` with a smaller prenorm grid (about -19% at T16384). Smoke 17/17.

- DSA runners: V3.2 and GLM-5.2 run `models/deepseek_v32` on 0.30 (`platforms/cuda.py` ranks `FLASH_ATTN_MLA_SPARSE` before `FLASHMLA_SPARSE` for head size 576). `kc_dsa_sparse_mla_runner.py`: bf16 KV -> FA3 sparse (`flash_attn_varlen_func(q=q_pe, q_v=ql_nope, block_table=indices, page size 1)` after `triton_convert(..., BLOCK_STRIDE_ROWS=64)`; no Q concat, no head padding; was FlashMLA `sparse_attn_fwd` with 64 padded heads); fp8_ds_mla stays FlashMLA sparse mixed batch, decode-only batches convert indices through the layer index group; the fp8 heads >= 32 separate path is not ported (fails loudly, no plan uses it). `kc_dsa_indexer_runner.py`: no in-range `-1` fill, prefill chunking by `DeepseekV32IndexerMetadataBuilder._split_indexer_prefill_chunks`, native `next_n` {1, 2, 4} on SM90 (was {1, 2}; next_n 4 paged logits 1075 -> 516 us), `SparseIndexerTopk('auto')` = cooperative up to 64 rows else persistent. `kc_dsa_cache_write_runner.py`: the standalone insert ops still exist (PCP path, recorded as `vllm030_model_path`), but the 0.30 model fuses both cache inserts with q/kv RMSNorm, RoPE, indexer-K quant and the top-k `-1` fill into one Triton `_fused_norm_rope_kernel`: new `--op fused_norm_rope`, plan `kc_dsa_fused_norm_rope__v030` (GLM-5.2 only; V3.2 config fields not available locally). 0.30 routes prefills with max sequence <= index_topk (2048) to dense MHA and skips the indexer; such cases still measure the sparse call and record `vllm030_default_route`. Other drift: FlashMLA `sparse_fp8` -> `sparse` namespace, Triton conversion kernel shown as `kernel`. Smoke 13/13.

## Candidate assembly (offline, CPU)

`python scripts/kernel_dataset/nvidia_h200/build_dataset.py assemble --kcampaign-root <dir with plans/ and runs/> --plan <plan> [<plan> ...]` writes one candidate per family to `profiler_output/kernel_dataset/nvidia_h200/kcampaign/candidates/<plan>/<family>.json.zst` plus `<family>.manifest.json` (per-case status and reason); only the small `window_NN.launch.json` / `.failure.json` files and `_provenance.json` are read, never the `.nsys-rep`. The case list is the plan itself, so H200-only cases need no A800 counterpart; `op_info.Attr` is rebuilt from the plan's `runner_args` plus the runner's launch evidence (for example `moe_tiling`, `kda_case`), never copied from A800. Selection is `nsys_nvtx_kernel_median`: windows with telemetry `clock_accepted` (1980 MHz before and after NVTX) that were captured after the 2026-09-26 03:14:29 CST single-process switch, newest three retained, 5% spread limit, median whole-trace window. Every window of a run must come from one vLLM stack (0.24 or 0.30, from `telemetry.environment.vllm_version`), recorded per entry in `h200_capture`. `gemm` / `vector` / `flash_attn` / `fused_moe` map to kernel-evaluation op types; `wq_fused_moe`, `kda`, `k3_mla`, `v4attn`, `dsa_*` are assembled with their own op Type and `evaluation_supported: false`. FlashAttention entries add `SP_PER_REQUEST` (FA3 `num_splits_dynamic` per request, decoded from the window's `fa3_scheduler_metadata`), `SP` (its maximum) and `FA3_SPLIT_COMBINE` (static split bound > 1, i.e. the combine kernel is launched even when every request runs one split); a case whose retained windows carry no such evidence is excluded as `missing_fa3_split_evidence`. `build_dataset.py check --candidate <file>` validates a candidate against the `nvidia_h200` evaluation timing contract.

### vLLM 0.24.0 inventory on SM90 (the capture host, caller-selected runtime, import/inspect only)

#### Kimi-K2.6 INT4 W4A16 (compressed-tensors `pack-quantized`, int, symmetric, group 32, `actorder: null`, routed experts only)

- Method: `CompressedTensorsMoEMethod.get_moe_method` (`quantization/compressed_tensors/compressed_tensors_moe/compressed_tensors_moe.py`) takes the `_is_wNa16_group_channel` branch; `check_moe_marlin_supports_layer` (`quantization/utils/marlin_utils.py`: `hidden % 128 == 0`, `intermediate_per_partition % max(64, group) == 0`, group in {-1,32,64,128}, no `apply_router_weight_on_input`) holds for 7168 / 256 (TP8) and 7168 / 2048 (EP8), so `CompressedTensorsWNA16MarlinMoEMethod` is used, not the Triton `CompressedTensorsWNA16MoEMethod` (that path is only reached when the Marlin shape check fails or on ROCm).
- Backend: `oracle/int_wna16.py::select_wna16_moe_backend` priority FLASHINFER_TRTLLM (`TrtLlmMxint4ExpertsMonolithic`, requires capability family 100) -> MARLIN (`MarlinExperts`, capability >= 7.5) -> BATCHED_MARLIN. SM90 standard activation format gets `MarlinExperts`. Weight key `kInt4Static32GroupScale`; scalar type `uint4b8` (symmetric, no zero points).
- Weight layout at load (`create_weights`, Marlin branch, `is_transposed`): `w13_weight_packed` int32 `(E, H/8, 2N)`, `w2_weight_packed` int32 `(E, N/8, H)`, scales BF16 `(E, H/32, 2N)` and `(E, N/32, H)`, g_idx `(E, H)` / `(E, N)`.
- Post-load: `convert_to_wna16_moe_kernel_format(WNA16MoEBackend.MARLIN, ...)` -> `_process_weights_marlin`: actorder None -> empty `(E, 0)` g_idx / sort indices; `ops.gptq_marlin_moe_repack(w, sort_idx, size_k, size_n, 4)`; `marlin_moe_permute_scales` (BF16 scales stay BF16 group-32). `VLLM_MARLIN_INPUT_DTYPE` unset -> BF16 activations (int8/fp8 activation variants not used; fp8 is rejected on SM90).
- Forward: `MarlinExperts.apply` -> `fused_marlin_moe` (`fused_moe/experts/marlin_moe.py`): `moe_align_block_size` (block_size_m from `M*topk/E_local/bm < 0.9` over {8,16,32,48,64}), per-call `marlin_make_workspace_new(device, 4)` (zero fill, `sms*4` int32), `ops.moe_wna16_marlin_gemm` (w13, `mul_topk_weights=False`), `apply_moe_activation` (SILU -> `torch.ops._C.silu_and_mul`), `ops.moe_wna16_marlin_gemm` (w2, `top_k=1`, `mul_topk_weights=True`), `ops.moe_sum` (`MarlinExperts.moe_sum`). Modular-kernel workspaces: workspace13 `(M*topk, max(N,H))`, workspace2 `(M*topk*max(2N,H),)`, output `(M,H)`, swapped into `intermediate_cache13=workspace2`, `intermediate_cache2=workspace13`. With EP, `expert_map` is passed and `output.zero_()` runs before the w2 GEMM.

#### MXFP4 experts on Hopper

- DeepSeek-V4-Flash / -Pro (`expert_dtype: fp4`, top-level `quant_method: fp8`): `models/deepseek_v4/quant_config.py::DeepseekV4FP8Config.get_quant_method` returns `Mxfp4MoEMethod` (`quantization/mxfp4.py`) for routed experts, which calls `oracle/mxfp4.py::select_deepseek_v4_mxfp4_moe_backend`. Priority `_get_priority_backends()`: FLASHINFER_TRTLLM_MXFP4_MXFP8 (`TrtLlmMxfp4Experts*`, capability family 100 only), DEEPGEMM_MXFP4 (`DeepGemmFP4Experts`, family 100/120 only), MARLIN, BATCHED_MARLIN. On SM90 -> MARLIN = `MarlinExperts` with `mxfp4_w4a16_moe_quant_config`, scalar type `float4_e2m1f`, BF16 activations; `gemm1_clamp_limit = swiglu_limit = 10.0` -> activation `torch.ops._C.silu_and_mul_with_clamp`. MegaMoE (`use_mega_moe`) is SM100 only. Marlin requires `hidden % 256 == 0` and `intermediate % 128 == 0` (`mxfp4_round_up_hidden_size_and_intermediate_size`; vLLM would pad, the runner refuses unpadded-illegal shapes instead). All V4 shapes in the plans are already aligned.
- Weight layout (`Mxfp4MoEMethod.create_weights`): uint8 `w13_weight (E, 2N, H/2)`, `w2_weight (E, H, N/2)`, uint8 UE8M0 scales `(E, 2N, H/32)`, `(E, H, N/32)`. Post-load `convert_weight_to_mxfp4_moe_kernel_format(MARLIN)` -> `marlin_utils_fp4.py::prepare_moe_mxfp4_layer_for_marlin`: per expert `ops.gptq_marlin_repack(W.view(int32).T, size_k, size_n, 4)`, scales -> BF16 -> `marlin_permute_scales` -> `mxfp4_marlin_process_scales` (`[0,2,1,3]` interleave, cast to `float8_e8m0fnu`). No global scale, no g_idx, no bias for V4.
- Forward: the same `fused_marlin_moe` sequence as INT4 (Marlin GEMM templated on `float4_e2m1f` weights with e8m0 group-32 scales).
- Kimi-K3 (`text_config.quantization_config`: compressed-tensors `mxfp4-pack-quantized`, float, 4 bit, group 32, uint8 scales): `get_moe_method` `_is_mxfp4` -> `CompressedTensorsW4A4Mxfp4MoEMethod`; `CutlassExpertsMxfp4._supports_current_device()` is False on SM90 (`ops.mxfp4_experts_quant_supported(90) == False`, checked on the capture host), so `MarlinExperts` with `prepare_moe_fp4_layer_for_marlin` (in-place twin of the MXFP4 prep above: same `gptq_marlin_repack` / `mxfp4_marlin_process_scales`). Despite the class name the activations are BF16 (W4A16).
- Not used on SM90 in vLLM 0.24: the gpt-oss path (`GptOssMxfp4MoEMethod` -> `select_mxfp4_moe_backend`, Triton `matmul_ogs` from `vllm/third_party/triton_kernels`, FlashInfer CUTLASS SM90 mixed GEMM) is reached only for `model_type == gpt_oss`; there is no MXFP4 -> FP8 weight conversion path for these models.

### Runner

One `fused_marlin_moe` call inside the NVTX range, arguments as `MarlinExperts.apply` passes them (workspaces and output preallocated outside, no Marlin `workspace` argument so the per-call zero fill is inside as in deployment, `ops.moe_sum`, `apply_moe_activation`). Synthetic weights (seed 42) are converted outside the range with the vLLM helpers above (`convert_to_wna16_moe_kernel_format`, `convert_weight_to_mxfp4_moe_kernel_format`). Routing is the `fused_moe_runner.py` seeded softmax/top-k (float32 weights) or an explicit `--expected-tok-per-expert-json` histogram (global experts); `--ep_size/--ep_rank` give contiguous local experts and the global->local `expert_map` (every rank routes all tokens: vLLM EP with all-gather/reduce-scatter dispatch). Launch evidence `wq_moe_routing`: `tok_per_expert` (global), `local_tok_per_expert`, `local_routed_pairs`, `marlin_block_size_m`, `num_tokens_post_padded`, `active_m_blocks`, format, scalar type, activation. Router top-k, modular-kernel prepare/finalize and EP communication are not in the range (same boundary as `fused_moe_runner.py`).

CLI: `--weight_format {int4_g32,mxfp4} --num_tokens --num_experts (global) --top_k --hidden_size --intermediate_size (per rank) --group_size 32 --ep_size --ep_rank [--swiglu_limit] [--expected-tok-per-expert-json] [--pre-nvtx-warmup-iterations 0]`.

### Unsupported / caveats

- Kimi-K3 is not a vLLM 0.24 model (no `KimiK3ForConditionalGeneration` in the registry) and its `hidden_act: situ` (`activation_situ_beta`, `activation_situ_linear_beta`) has no `MoEActivation`; `MarlinExperts` would reject it. K3 cases therefore measure the K3 Marlin MXFP4 GEMM shapes with a SiLU-and-mul activation kernel as a stand-in; the activation launch must not be used as K3 evidence (the GEMM, align, zero-fill and moe_sum launches are shape-exact).
- EP variants cover the expert computation of rank 0 only; all-to-all / all-gather traffic is not measured.
- Plan results land in `runs/<plan>/cases/<case>/window_01.*`; the smoke windows below are canonical-protocol windows of the same runner snapshot.

## Family: H200 KDA and DeepSeek-V4 attention kernel captures

Runners, plans and inventory for the next-generation attention kernels of Kimi-K3 (Kimi Delta Attention, Gated MLA) and DeepSeek-V4 (CSA / HCA / SWA sparse MLA, KV compressor, mHC) on `nvidia_h200` with the vLLM 0.24.0 stack (torch 2.11, triton 3.6, flashinfer 0.6.12, tilelang 0.1.9, cutlass-dsl). Every case is measured with the canonical `nsys_nvtx_kernel_median` protocol through `scripts/kernel_dataset/nvidia_h200/nsys_campaign_runner.py` and `H200CaptureSession` (GPU lock, identity check, power warm-up, 1980 MHz clock gate); one runner call = one NVTX range.

#### DeepSeek-V4

- Model: `vllm/models/deepseek_v4/` (`DeepseekV4ForCausalLM`). Attention class on NVIDIA non-SM12: `nvidia/flashmla.py::DeepseekV4FlashMLAAttention` (backend `FLASHMLA_SPARSE_DSV4`, `sparse_mla.py`); FlashInfer sparse (`nvidia/flashinfer_sparse.py`) is the SM12 default or an explicit opt-in.

- KV cache format `fp8_ds_mla` for V4: 584 B/token (448 FP8 NoPE + 64 BF16 RoPE + 8 UE8M0 scales, 7 used); SWA pages 64 tokens, compressed pages `block_size // ratio` (recipes use `--block-size 256`, so 64 for C4A, 2 for C128A). This differs from the V3.2 656 B/token layout and from the V3.2 call (no attn_sink / extra cache), so V4 CSA/HCA/SWA are captured here and not by the DSA runner.
- KV compressor (`compressor.py::DeepseekCompressor.forward`): `save_partial_states` (Triton) + `compress_norm_rope_store_cutedsl` (C4: fused `fused_kv_compress_norm_rope_insert_sparse_attn_cutedsl`; C128: split `split_kv_compress_norm_rope_insert_sparse_attn_cutedsl`); state cache fp32 `[pages, 4 or 8, 2*coff*512]`, `kv_score` fp32 `[N, 2*coff*512]` (coff 2 for the overlapping C4 compressor), `cos_sin_cache` fp32, positions / slot mappings int64.
- mHC: `vllm/model_executor/kernels/mhc/tilelang.py` (`mhc_pre_tilelang` on the first layer, `mhc_fused_post_pre_tilelang` at every later attention/FFN boundary, `mhc_post_tilelang`, `hc_head_fused_kernel_tilelang` at the model head); residual `[T, hc_mult=4, hidden]` bf16, `fn` fp32 `[(2+hc)*hc, hc*hidden]`, 20 Sinkhorn iterations. Distinct kernels, captured here.
- V4 indexer (C4A layers) runs `SparseAttnIndexer` (the V3.2/GLM-5.2 DSA indexer op) over the C4-compressed index keys (index_n_heads 64, index_head_dim 128, top-k 512 / 1024, keys = context / 4) plus `fused_indexer_q_rope_quant` and a head-128 Triton compressor. It is the DSA-indexer family and is not captured here.

### Runners (`scripts/kernel_dataset/nvidia_h200/`)

All three copy the H200 capture-session pattern of `flash_attn_runner.py` (`open_h200_capture_session` -> `validate_device` -> inputs -> `power_warmup` -> 5 warm-up calls -> one call inside one NVTX range -> launch evidence -> `finish`). Per-step metadata that vLLM builds in the metadata builder (not per layer) is built before the NVTX range and recorded in the telemetry evidence.

- `kc_dsa_sparse_mla_runner.py` -- one `FlashMLASparseImpl.forward_mqa` for `--batch` requests of `--q-len` tokens with `--context` KV tokens each; path chosen by vLLM's own rules from `--num-heads` and `--kv-cache-dtype {bf16,fp8_ds_mla}`; `--num-speculative-tokens` gives the decode/prefill split for the separate path. Top-k indices are distinct uniform random request-local positions inside each token's causal context (-1 padded when shorter than topk); the fp8 cache is populated with `concat_and_cache_mla` so the scales are valid; `FlashMLASchedMeta` is initialised in warm-up and reused by the NVTX call (steady state of layers 2..L in one step).
- `kc_dsa_indexer_runner.py` -- `--phase decode` (paged logits + cooperative/persistent top-k, H200 native/flatten rule) or `--phase prefill` (vLLM's chunk split, gather + logits + prefill top-k per chunk). Includes the `topk_indices_buffer[:T] = -1` fill.
- `kc_dsa_cache_write_runner.py` -- `--op {indexer_k, mla_fp8_ds_mla, mla_bf16}` with `--slot-layout {prefill, decode}`.

At TP8 both models have < 32 heads per rank, so both fp8 plans take the mixed-batch FlashMLA sparse decode kernel with heads padded to 64 and both bf16 plans take `flash_mla_sparse_fwd` padded to 64: the V3.2 H16 cases exercise the same attention kernel as GLM H8 and differ only in the Q concat/pad kernels.

Regenerate with `python3 microbench/nvidia_h200/kcampaign/make_dsa_plans.py`; run with `REPO=<snapshot> PY=<runtime-python> NSYS=<profiler-executable> CUDA_HOME=<toolkit> <public-root>/h200_microbench/kcampaign/launch.sh <gpu> kc_dsa_<plan>`.

### Not covered

- DeepSeek-V4 CSA/HCA: vLLM 0.24 runs it through `models/deepseek_v4/` with a different cache (584 B/token, ue8m0 scales, 448 NoPE), an extra SWA cache (`extra_k_cache`/`extra_indices_in_kvcache` of `flash_mla_with_kvcache`), a compressed indexer cache (`DeepseekV4IndexerBackend`, block 256, `compress_ratio`) and its own compressor kernels; these runners do not reproduce that call sequence.
- FP4 indexer cache (`use_fp4_indexer_cache`) is SM100-only.
- The separate prefill/decode fp8 path (heads per rank >= 32, e.g. DP attention) is implemented in the sparse-MLA runner but no plan uses it.
- Q copies that PyTorch issues as `cudaMemcpyAsync` (e.g. the head-pad copy when the padded slice is contiguous, T=1) are not kernels and are not in the kernel-timing total.
- Indexer Q/K projections, `per_token_group_quant_fp8`, the K LayerNorm/RoPE and the MLA W_UK/W_UV bmm are GEMM/vector ops outside this campaign.
